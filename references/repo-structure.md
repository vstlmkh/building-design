# Repo structure

The directory contract for a `design/` workspace, the manifest that describes it, and the
handoff file that lets an AI coding agent reproduce the design exactly.

## Contents

- Where `design/` lives
- The tree
- `design.config.json`
- What is committed vs generated
- `handoff/AGENTS.md` — the implementation contract
- Naming rules that make handoff work

## Where `design/` lives

Three placements, in order of preference:

1. **`design/` inside the product repo** — default. Design and code move in the same PR, so
   they cannot drift. Choose this unless the operator says otherwise.
2. **A standalone design repo** (`<product>-design`) consumed as a git submodule or npm/pub
   package. Choose when several apps share one system, or designers have no access to the
   product repo.
3. **A `design/` package inside a monorepo** (`packages/design/`). Same contract, wired into
   the workspace tooling.

The tree below is identical in all three; only the root differs. Record the choice in
`design.config.json` so later sessions do not re-ask.

## The tree

```
design/
├── README.md                     # what this is, how to run the prototype, how to contribute
├── design.config.json            # manifest — the entry point for humans and agents
├── CHANGELOG.md                  # one line per landed design change, newest first
│
├── brand/
│   ├── brand.md                  # positioning, personality, voice & tone, do / don't
│   ├── logo/
│   │   ├── logo-primary.svg      # full lockup, light background
│   │   ├── logo-inverse.svg      # full lockup, dark background
│   │   ├── logo-mono.svg         # single-colour, currentColor
│   │   ├── wordmark.svg
│   │   └── mark.svg              # the favicon-safe glyph — NOT the full logo
│   ├── clearspace.md             # min sizes, clear space, misuse examples
│   └── imagery.md                # photography / illustration / 3D direction
│
├── tokens/
│   ├── primitives.tokens.json    # tier 1 — raw ramps: colour, space, size, radius, type, motion
│   ├── semantic.tokens.json      # tier 2 — intent, with per-theme values (light + dark)
│   ├── components.tokens.json    # tier 3 — only where a semantic token is too broad
│   └── build/                    # GENERATED by build_tokens.py — gitignored
│       ├── tokens.css            #   CSS custom properties, :root + [data-theme="dark"]
│       ├── tokens.ts             #   typed constants for web
│       ├── tokens.dart           #   Flutter ThemeData-ready
│       ├── Tokens.swift          #   SwiftUI Color/Font extensions
│       ├── Tokens.kt             #   Compose
│       └── colors.xml            #   Android res/values + values-night
│
├── icons/
│   ├── ui/                       # in-product icon set — 24px grid SVGs, currentColor
│   │   └── <name>.svg
│   ├── app/
│   │   ├── master.svg            # THE source for every launcher/store icon
│   │   ├── master-dark.svg       # optional iOS/Android dark variant source
│   │   └── build/                # GENERATED by build_icons.py — gitignored
│   │       ├── web/              #   favicon.ico, favicon.svg, apple-touch-icon.png,
│   │       │                     #   icon-192/512.png, maskable-512.png, site.webmanifest
│   │       ├── ios/              #   AppIcon.appiconset/ (+ Contents.json), light/dark/tinted
│   │       └── android/          #   mipmap-*/ic_launcher_foreground|background|monochrome,
│   │                             #   ic_launcher.xml, play-store-512.png
│   └── icons.manifest.json       # name → keywords → usage, for agent lookup
│
├── ui-kit/
│   ├── README.md                 # inventory table: component → status → prototype route
│   └── components/<Component>/
│       ├── spec.md               # anatomy, variants, states, sizes, tokens used, a11y, motion
│       └── <Component>.js        # the prototype implementation (web component or render fn)
│
├── ux/
│   ├── personas.md
│   ├── stories.md                # US-### — one table, the backlog of user stories
│   ├── flows/FLOW-###-<slug>.md  # mermaid flowchart + decision points + failure branches
│   └── screens/SCR-###-<slug>.md # screen spec: purpose, states, components, copy, traces
│
├── prototype/                    # THE source of visual truth — zero install
│   ├── run.sh                    # python3 -m http.server … ; do not open index.html directly
│   ├── index.html
│   ├── app.js                    # router, theme toggle, route registry
│   ├── styles/                   # base.css, utilities.css + symlink/copy of tokens.css
│   ├── routes/                   # one module per screen / page / UI-kit gallery entry
│   └── motion.js                 # shared easing + duration helpers bound to motion tokens
│
├── variants/                     # A–E exploration rounds; see lifecycle below
│   └── YYYY-MM-DD-<slug>/
│       ├── BRIEF.md              # the operator prompt + answered clarifications
│       ├── A/ … E/               # one prototype route per variant
│       └── DECISION.md           # chosen variant, rationale, why each other was rejected
│
├── handoff/
│   ├── AGENTS.md                 # the implementation contract — see below
│   ├── platform-map.md           # token → CSS / Flutter / SwiftUI / Compose mapping table
│   └── exports/                  # PNG/SVG frame exports for tickets and reviews
│
└── decisions/ADR-###-<slug>.md   # design decisions with lasting consequences
```

## `design.config.json`

The manifest. Every agent and script reads this first; it is the only file whose shape is
fixed.

```json
{
  "$schema": "./design.config.schema.json",
  "product": "Acme",
  "version": "0.3.0",
  "placement": "in-product-repo",
  "platforms": ["web", "ios", "android"],
  "themes": ["light", "dark"],
  "defaultTheme": "light",
  "paths": {
    "tokens": "tokens",
    "icons": "icons",
    "uiKit": "ui-kit",
    "ux": "ux",
    "prototype": "prototype",
    "variants": "variants",
    "handoff": "handoff"
  },
  "prototype": { "command": "./prototype/run.sh", "port": 4321 },
  "targets": {
    "web": { "framework": "react", "styling": "css-custom-properties" },
    "ios": { "framework": "swiftui" },
    "android": { "framework": "compose" }
  },
  "conventions": {
    "componentNaming": "PascalCase",
    "tokenNaming": "kebab-case-dot-path",
    "iconGrid": 24
  }
}
```

`platforms` drives which icon packs and token outputs are required — a web-only product is not
failed for having no `AppIcon.appiconset`.

## What is committed vs generated

| Committed (source)                              | Generated (gitignore)        |
| ----------------------------------------------- | ---------------------------- |
| `*.tokens.json`, brand SVGs, `icons/app/master.svg`, `icons/ui/*.svg` | `tokens/build/`, `icons/app/build/` |
| `ui-kit/**`, `prototype/**`, `ux/**`, `variants/**/DECISION.md`        | `handoff/exports/` (optional — commit when tickets link to them) |

Rule: if a teammate cannot regenerate it with `build_tokens.py` / `build_icons.py`, it is a
source and must be committed. The scaffold writes the matching `design/.gitignore`.

## `handoff/AGENTS.md` — the implementation contract

This is what makes the design machine-reproducible. A coding agent asked to "implement the
settings screen" should need this file and nothing else to find its way. Keep it short and
pointer-heavy; the detail lives in the files it points at.

Required sections:

1. **Read order** — `design.config.json` → `tokens/build/<platform file>` →
   `ui-kit/README.md` → the `SCR-###` spec → the prototype route.
2. **Hard rules for implementers** — never hardcode a colour, size, radius, duration, or
   font; every value resolves to a token. Component names in code match `ui-kit/components/`
   exactly. Every state in `spec.md` must exist in code.
3. **Token → platform mapping** — point at `platform-map.md`; name the generated file per
   target so the agent imports the right one.
4. **How to verify** — run the prototype on the documented port, open the named route,
   compare side by side with the implementation; list the states that must be checked.
5. **Open questions / intentional divergences** — where the platform *should* differ (native
   navigation, system fonts, haptics) so an agent does not "fix" a deliberate choice.

## Naming rules that make handoff work

Design-to-code drift is nearly always a naming problem. Enforce:

- One name per concept across design, prototype, and code. `ButtonPrimary` in the UI kit is
  `ButtonPrimary` in React/Compose/SwiftUI — not `PrimaryButton`.
- Token paths are dot-separated, tier-prefixed, intent-named:
  `color.bg.surface.raised`, not `color.gray.100`. Primitives keep the raw name
  (`color.palette.slate.100`) and are referenced only by semantic tokens.
- Screen and flow IDs (`SCR-012`, `FLOW-003`, `US-027`) appear in the spec, the prototype
  route (`/screens/scr-012-settings`), and the implementation ticket. Traceability is the
  point.
- Icon names are function-first, not picture-first: `action.delete`, not `trash-can`.

## Variants folder lifecycle

1. `new_round.py <slug>` creates `variants/YYYY-MM-DD-<slug>/` with `BRIEF.md`, `A/`–`E/`
   route stubs, and an empty `DECISION.md`.
2. Variants render live in the prototype under `/variants/<slug>/<letter>`.
3. On approval: the chosen variant's code moves into `ui-kit/` or `prototype/routes/`,
   `DECISION.md` is filled in, and the other letters' route files are deleted.
4. `DECISION.md` is kept forever. Rounds are never deleted — they are the design's history.
